Kubernetes Architecture

Two diagrams to build your mental model before diving into commands. You only need to understand these two pictures to get started.

What is a cluster?

Your app runs in Pods. Pods live on worker nodes. The control plane decides which node each pod goes on. You talk to all of it through kubectl.

What objects will you actually use?

Everything inside the dashed border lives in a namespace. Namespaces are how you divide a cluster between teams, environments, or apps — objects in different namespaces are isolated by default.
🔑

Kubeconfig

The kubeconfig file tells kubectl which cluster to talk to, which user credentials to use, and which namespace to default to. Before running any command, kubectl needs to find this file.

Ways to set the kubeconfig

MethodHowScope
Default location ~/.kube/config Always loaded if present. No action needed.
Environment variable export KUBECONFIG=/path/to/config Current shell session only. Overrides the default.
Multiple files merged export KUBECONFIG=~/.kube/config:~/other-config Colon-separated list — all files are merged at runtime.
Per-command flag kubectl --kubeconfig=/path/to/config get pods Single command only. Highest precedence.
In-cluster (pods) Automatic via service account token mount Used when kubectl runs inside a pod in the cluster.
ℹPrecedence order: --kubeconfig flag > KUBECONFIG env var > ~/.kube/config. The flag always wins.

Common kubeconfig commands

CommandDescription
kubectl config viewPrint the merged kubeconfig (all loaded files).
kubectl config get-contextsList all contexts with cluster, user, and namespace.
kubectl config current-contextShow which context is active right now.
kubectl config use-context <ctx>Switch the active context.
kubectl config set-context --current --namespace=<ns>Change the default namespace for the current context.
kubectl config rename-context <old> <new>Rename a context (useful when cloud CLIs generate verbose names).
kubectl config delete-context <ctx>Remove a context entry from the kubeconfig.
💡When you run aws eks update-kubeconfig, gcloud container clusters get-credentials, or az aks get-credentials, they write a new context into ~/.kube/config automatically.

Anatomy of a kubeconfig

A kubeconfig has three sections. A context is just a named pointer that binds one cluster + one user + one namespace together.

clusters:            # connection details (server URL, CA cert)
  - name: my-cluster
    cluster:
      server: https://1.2.3.4
      certificate-authority-data: <base64>

users:               # credentials (token, cert, or exec plugin)
  - name: my-user
    user:
      token: eyJhbGci...

contexts:            # named bindings of cluster + user + namespace
  - name: dev
    context:
      cluster: my-cluster
      user: my-user
      namespace: default

current-context: dev  # which context kubectl uses right now
⚠Never commit a kubeconfig to git — it contains credentials. Add ~/.kube/config to your .gitignore and use short-lived tokens or IRSA/Workload Identity in production.

Namespaces

A namespace is a logical boundary inside a cluster. Every resource (pods, services, deployments…) lives in exactly one namespace. They let you divide a cluster between teams or environments — for example dev, staging, and prod can all run in the same cluster without stepping on each other. Kubernetes ships with four built-in namespaces: default (where your resources land if you don't specify one), kube-system (cluster internals — don't touch), kube-public (readable by everyone, rarely used), and kube-node-lease (node heartbeats). Almost every kubectl command scopes to the current namespace unless you pass -n <namespace> or -A (all namespaces).

CommandDescription
kubectl get namespacesLists all namespaces and their phase (Active / Terminating).
kubectl create namespace <n>Creates a new namespace imperatively.
kubectl describe namespace <n>Shows labels, annotations, ResourceQuotas, LimitRanges.
kubectl delete namespace <n>Deletes the namespace and all resources inside it.
✦Alias: kubectl get ns — namespace stuck in Terminating usually has finalizers blocking deletion.
✦Set a default namespace: kubectl config set-context --current --namespace=<n>

Pods

CommandDescription
kubectl get podsLists pods in the default namespace.
kubectl get pods -n <ns>Scopes listing to a specific namespace.
kubectl get pods -ALists pods across ALL namespaces.
kubectl get pods -n <ns> -o wideAdds node name, IP, nominated node, readiness gates.
kubectl describe pod <n> -n <ns>Full detail: events, conditions, resources, volumes.
kubectl logs <pod> -n <ns>Streams stdout/stderr of the main container.
kubectl logs <pod> -n <ns> -c <container>Logs from a specific container in a multi-container pod.
kubectl logs <pod> -n <ns> --previousLogs from the previous (crashed) container instance.
kubectl exec -it <pod> -n <ns> -- bashOpens an interactive shell inside the pod.
kubectl delete pod <n> -n <ns>Deletes the pod (controller will recreate if managed).
✦kubectl get pods -n <ns> --watch streams live status changes.
⚠Deleting a pod managed by a Deployment/StatefulSet just triggers a restart. Scale down the controller to truly stop it.

Nodes

Worker machines in your cluster (VMs or bare metal). Inspect them to debug scheduling failures, resource pressure, and hardware issues.

CommandDescription
kubectl get nodesLists nodes with status, roles, age, and Kubernetes version.
kubectl get nodes -o wideAdds internal/external IPs, OS image, kernel, container runtime.
kubectl describe node <n>Full detail: capacity, allocatable, conditions, taints, events.
kubectl top nodeLive CPU and memory usage per node (requires metrics-server).
kubectl cordon <n>Marks node unschedulable — no new pods placed on it.
kubectl uncordon <n>Re-enables scheduling on the node.
kubectl drain <n> --ignore-daemonsets --delete-emptydir-dataSafely evicts all pods before node maintenance.
kubectl label node <n> disktype=ssdAdds a label used for nodeSelector or nodeAffinity.
✦Standard maintenance workflow: cordon → drain → maintain → uncordon.
⚠kubectl drain fails on pods with local storage unless --delete-emptydir-data is passed. Add --force for unmanaged pods.

Services

Stable DNS name and IP for a dynamic set of pods selected by labels. The three main types build on each other — LoadBalancer wraps NodePort which wraps ClusterIP.

TypeScopeUse case
ClusterIPInternal onlyDefault. Pod-to-pod communication inside the cluster.
NodePortNode IP + static port (30000–32767)Dev/testing or on-prem without a cloud LB.
LoadBalancerCloud LB → NodePort → ClusterIPProduction external traffic. Provisions a cloud load balancer.
CommandDescription
kubectl get services -n <ns>Lists services, types, ClusterIPs, external IPs, and ports.
kubectl describe svc <n> -n <ns>Shows selector, endpoints, port mappings, and events.
kubectl expose deployment <n> --port=80 --target-port=8080 -n <ns>Creates a ClusterIP service pointing at a Deployment.
kubectl delete svc <n> -n <ns>Removes the service (pods keep running).
✦Alias: kubectl get svc  |  port-forward: kubectl port-forward svc/<n> 8080:80 -n <ns>
ℹUse kubectl get svc -n <ns> -w to watch for the external IP after creating a LoadBalancer — starts as <pending>.

Service type manifests

yaml
# ClusterIP (default — internal only)
spec:
  type: ClusterIP
  selector: { app: my-app }
  ports: [{ port: 80, targetPort: 8080 }]

# NodePort — opens port on every node
spec:
  type: NodePort
  ports: [{ port: 80, targetPort: 8080, nodePort: 30080 }]

# LoadBalancer — provisions a cloud LB
spec:
  type: LoadBalancer
  ports: [{ port: 80, targetPort: 8080 }]

Deployments

Manage stateless workloads with desired replica counts, rolling updates, and rollback. Internally own a ReplicaSet.

CommandDescription
kubectl get deployments -n <ns>Lists with READY/UP-TO-DATE/AVAILABLE counts.
kubectl describe deployment <n> -n <ns>Shows strategy, pod template, replica history, and events.
kubectl create deployment <n> --image=nginx:1.25 -n <ns>Creates a deployment imperatively.
kubectl scale deployment <n> --replicas=3 -n <ns>Scales to the desired replica count immediately.
kubectl set image deployment/<n> <c>=nginx:1.26 -n <ns>Triggers a rolling update by updating the container image.
kubectl rollout status deployment/<n> -n <ns>Watches rollout progress until complete.
kubectl rollout history deployment/<n> -n <ns>Lists revision history with change-cause annotations.
kubectl rollout undo deployment/<n> -n <ns>Rolls back to the previous revision.
kubectl rollout undo deployment/<n> --to-revision=2 -n <ns>Rolls back to a specific revision number.
kubectl delete deployment <n> -n <ns>Deletes deployment and all its pods.
✦Alias: kubectl get deploy  |  Annotate: kubectl annotate deployment/<n> kubernetes.io/change-cause='reason'

StatefulSets

For stateful workloads needing stable network identities, ordered startup/shutdown, and persistent storage per replica. Pods get stable hostnames: <n>-0, <n>-1, <n>-2 ...

CommandDescription
kubectl get statefulsets -n <ns>Lists StatefulSets with READY and AGE.
kubectl describe sts <n> -n <ns>Shows pod template, volumeClaimTemplates, and update strategy.
kubectl scale sts <n> --replicas=5 -n <ns>Scales up/down in strict ordinal order.
kubectl rollout status sts/<n> -n <ns>Watches StatefulSet rollout progress.
kubectl rollout undo sts/<n> -n <ns>Rolls back to the previous revision.
kubectl delete sts <n> -n <ns>Deletes StatefulSet but NOT its PersistentVolumeClaims.
✦Alias: kubectl get sts  |  DNS per pod: <pod>.<headless-svc>.<ns>.svc.cluster.local
⚠Deleting a StatefulSet does NOT delete PVCs. Delete manually: kubectl delete pvc -l app=<n> -n <ns>

ConfigMaps

Store non-sensitive configuration as key-value pairs. Consumed as environment variables or mounted as files.

CommandDescription
kubectl get configmaps -n <ns>Lists ConfigMaps in the namespace.
kubectl describe cm <n> -n <ns>Shows all keys and their values in plain text.
kubectl create cm <n> --from-literal=KEY=VAL -n <ns>Creates from inline key-value pairs.
kubectl create cm <n> --from-file=config.yaml -n <ns>Creates from a file (filename becomes the key).
kubectl create cm <n> --from-env-file=.env -n <ns>Creates from a .env file.
kubectl edit cm <n> -n <ns>Opens in $EDITOR for live editing.
kubectl delete cm <n> -n <ns>Deletes the ConfigMap.
⚠Pods do NOT auto-reload env-var ConfigMaps on change — requires pod restart. Volume-mounted ConfigMaps auto-refresh (~60s kubelet sync delay).

Secrets

Store sensitive data (passwords, tokens, TLS certs). Base64-encoded at rest. Enable EncryptionConfiguration for true at-rest encryption in etcd.

CommandDescription
kubectl get secrets -n <ns>Lists secrets — values hidden, only names and types shown.
kubectl describe secret <n> -n <ns>Shows keys and byte sizes — never decoded values.
kubectl get secret <n> -n <ns> -o jsonpath='{.data.pw}' | base64 -dDecodes a specific key to plain text.
kubectl create secret generic <n> --from-literal=pw=s3cr3t -n <ns>Creates an Opaque secret from a literal.
kubectl create secret tls <n> --cert=tls.crt --key=tls.key -n <ns>Creates a kubernetes.io/tls typed secret.
kubectl create secret docker-registry <n> ... -n <ns>Creates an image pull secret for a private registry.
kubectl delete secret <n> -n <ns>Deletes the secret.
⚠Never commit Secret manifests with plaintext values to git. Use Sealed Secrets, External Secrets Operator, or Vault.
✦Audit access: kubectl auth can-i get secrets -n <ns>

Ingress

Routes external HTTP/HTTPS traffic to services based on hostname and path rules. Requires a controller to implement the rules.

⚠Controller status (March 2026): The ingress-nginx community controller reached EOL — no security patches. The Ingress API itself is NOT deprecated (GA, stable, feature-frozen). Active alternatives: Envoy Gateway, Cilium, NGINX Gateway Fabric (F5), Traefik, Kong.
CommandDescription
kubectl get ingress -n <ns>Lists Ingress resources with hosts, paths, and backends.
kubectl describe ingress <n> -n <ns>Shows rules, TLS config, backend endpoints, and events.
kubectl get ingress -ALists all Ingress resources across all namespaces.
kubectl delete ingress <n> -n <ns>Deletes the Ingress (controller stops routing, pods keep running).
✦Alias: kubectl get ing  |  Audit controller: kubectl get pods -A -l app.kubernetes.io/name=ingress-nginx

Example Ingress manifest

yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app
  namespace: production
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  ingressClassName: nginx          # or envoy, cilium, traefik
  tls:
    - hosts: [app.example.com]
      secretName: app-tls
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: my-app
                port: { number: 80 }
ℹGateway API (modern replacement) splits into Gateway (infra team) + HTTPRoute (app team). See gateway-api.sigs.k8s.io.

Volumes & Persistent Storage

Volumes give pods access to storage that survives container restarts. Key resources: PersistentVolume (PV — the actual disk) and PersistentVolumeClaim (PVC — pod's request for storage).

CommandDescription
kubectl get pvLists PersistentVolumes (cluster-scoped, no namespace).
kubectl get pvc -n <ns>Lists PersistentVolumeClaims in the namespace.
kubectl describe pvc <n> -n <ns>Shows binding status, capacity, access mode, and StorageClass.
kubectl get storageclassLists available StorageClasses (dynamic provisioners).
kubectl delete pvc <n> -n <ns>Deletes the claim (PV reclaim policy governs the disk).
TypeSurvives restart?Survives deletion?Use case
emptyDir✅ Yes❌ NoTemp scratch space, shared between containers in a pod
hostPath✅ Yes✅ Same nodeDev/testing only — ties pod to a specific node
PVC✅ Yes✅ YesProduction persistent storage (databases, uploads)
configMap / secret✅ Yes✅ YesMount config files or certs into the container filesystem
⚠A PVC stuck in Pending usually means no StorageClass matched or no PV available with the right access mode and capacity.

Example PVC + pod mount

yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
  namespace: production
spec:
  accessModes: [ReadWriteOnce]   # RWO one node | ROX many read-only | RWX many read-write
  storageClassName: standard
  resources:
    requests:
      storage: 5Gi
---
spec:
  containers:
    - name: app
      volumeMounts:
        - name: data
          mountPath: /var/app/data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: app-data

Resource Requests & Limits

Tell the scheduler how much CPU/memory a pod needs (requests) and the hard cap it cannot exceed (limits). Without these, pods compete blindly for node resources.

FieldWhen it appliesEffect if exceeded
requestsScheduling timePod won't be placed on a node without enough available
limits (memory)RuntimeContainer is OOMKilled immediately
limits (cpu)RuntimeContainer is throttled (slowed), not killed
⚠No requests/limits = BestEffort pod — first to be evicted under node memory pressure.
ℹCPU units: 1 = 1 core, 500m = half core, 100m = 0.1 core. Memory: use Mi/Gi not M/G.
yaml
resources:
  requests:
    cpu: "100m"        # scheduler: need at least 0.1 core
    memory: "128Mi"    # scheduler: need at least 128Mi
  limits:
    cpu: "500m"        # runtime: throttle if > 0.5 core
    memory: "256Mi"    # runtime: OOMKill if > 256Mi
✦Check live usage: kubectl top pods -n <ns>  |  Debug OOMKill: kubectl describe pod <n> -n <ns> → look for OOMKilled in Last State.

Probes

Let Kubernetes know if a container is alive, ready for traffic, or still starting up. Without them, Kubernetes assumes healthy the moment the process starts.

ProbePurposeEffect if it fails
livenessProbeIs the container still alive?Container is restarted
readinessProbeIs the container ready for traffic?Pod removed from Service endpoints — no traffic sent
startupProbeHas the container finished starting?Disables liveness/readiness until it passes — prevents premature restarts
⚠Failing readinessProbe silently removes pod from service endpoints — requests stop but pod keeps running. Most common cause of "deployment running but requests failing".
yaml
startupProbe:             # guards slow-starting apps (JVM, DB migrations)
  httpGet: { path: /healthz, port: 8080 }
  failureThreshold: 30   # 30 × 10s = up to 5 min to start
  periodSeconds: 10

livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 15
  failureThreshold: 3    # restart after 3 consecutive failures

readinessProbe:
  httpGet: { path: /ready, port: 8080 }   # separate endpoint from liveness
  periodSeconds: 5
  failureThreshold: 3
✦Use separate /healthz (liveness) and /ready (readiness) endpoints. Readiness can fail during DB migrations without restarting the pod.
ℹUse startupProbe for slow-starting apps (JVM warmup, migrations). Without it, livenessProbe can kill the container before it ever becomes ready.

RBAC

Controls who (or what service) can do what in the cluster. Four key resources work together to grant permissions.

ResourceScopePurpose
ServiceAccountNamespaceIdentity for a pod or process
RoleNamespaceSet of permissions within one namespace
ClusterRoleClusterSet of permissions across the whole cluster
RoleBindingNamespaceGrants a Role to a user/group/ServiceAccount
ClusterRoleBindingClusterGrants a ClusterRole cluster-wide
CommandDescription
kubectl get serviceaccounts -n <ns>Lists ServiceAccounts in the namespace.
kubectl get roles -n <ns>Lists Roles in the namespace.
kubectl get rolebindings -n <ns>Lists RoleBindings in the namespace.
kubectl get clusterrolesLists cluster-wide roles.
kubectl describe role <n> -n <ns>Shows what verbs/resources the Role grants.
kubectl auth can-i <verb> <resource> -n <ns>Checks if your current identity has a permission.
kubectl auth can-i --list -n <ns>Lists everything your current identity can do in a namespace.
kubectl auth can-i get pods -n <ns> --as=system:serviceaccount:<ns>:<sa>Checks permissions for a specific ServiceAccount.
✦Aliases: kubectl get sa, kubectl get rb, kubectl get crb
⚠Every pod gets the default ServiceAccount if unspecified. Always create a dedicated SA with least-privilege permissions for each workload.

Example: ServiceAccount + Role + RoleBinding

yaml
# 1. Identity for the pod
apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-reader
  namespace: production
---
# 2. Permissions (namespace-scoped)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: production
rules:
  - apiGroups: [""]               # "" = core API group
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---
# 3. Bind Role to ServiceAccount
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app-reader-binding
  namespace: production
subjects:
  - kind: ServiceAccount
    name: app-reader
    namespace: production
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
---
# 4. Use the ServiceAccount in a pod
spec:
  serviceAccountName: app-reader
  containers:
    - name: app
      image: my-app:1.0.0
ℹUse Role for namespace-scoped app workloads. Use ClusterRole only for cluster-wide needs (monitoring agents, operators, CI/CD runners).
